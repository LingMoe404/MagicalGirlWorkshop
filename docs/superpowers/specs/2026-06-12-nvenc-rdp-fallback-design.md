# NVENC 远程桌面解码降级设计

## 目标

修复 NVIDIA AV1 转码在远程桌面锁屏或断开后失败的问题，同时保持现有 NVENC 编码质量参数不变，并避免把所有 FFmpeg 错误都误报成字幕错误。

## 根本原因

NVIDIA 转码路径目前向 FFmpeg 传入 `-hwaccel auto`。在 Windows 上，项目内置的 FFmpeg 会自动选择 DXVA2。DXVA2 需要创建与当前图形桌面会话相关的 Direct3D 设备。

当远程桌面会话锁定或断开后，DXVA2 可能无法创建 Direct3D 设备。此时 NVIDIA 显卡和 NVENC 编码器实际上仍然可用，但硬件解码初始化已经失败，因此正式转码无法开始。

当前的重试逻辑还存在另一个问题：无论 FFmpeg 第一次因为什么原因失败，程序都会假定是字幕损坏，并在删除字幕流后重试。因此硬件设备错误会被错误地显示为字幕错误。

## 解码方案

- 启用 GPU 解码并使用 `av1_nvenc` 时，明确指定 CUDA 解码，不再使用 `-hwaccel auto`。
- 保持现有 `av1_nvenc` 编码器、CQ、预设、像素格式、AQ、音频、色彩和输出参数不变。
- 如果 FFmpeg 明确报告硬件解码或设备初始化失败，只对当前文件改用 CPU 软件解码后重试。
- 降级后只有解码环节改由 CPU 执行，编码环节仍然使用 NVENC，因此不会改变目标编码质量参数。

## 错误分类与尝试次数

每个文件最多执行三次 FFmpeg 转码尝试：

1. 使用首选解码方式，并保留字幕。
2. 如果上一次属于硬件设备错误，则改用 CPU 软件解码，并继续保留字幕。
3. 如果某次尝试明确属于字幕错误，则删除字幕流，并保留当前已经选定的解码方式再次尝试。

只有识别为硬件设备错误时，才允许切换到 CPU 软件解码。只有识别为字幕错误时，才允许删除字幕。无法识别的错误不会盲目重试，而是立即停止当前文件，并显示真实的 FFmpeg 错误日志。

如果错误出现顺序相反，例如第一次先遇到字幕错误，则第二次先删除字幕；如果之后又出现硬件设备错误，第三次可以在无字幕状态下切换到 CPU 软件解码。已经使用过的降级状态不会重复。

## 代码结构

在 `workers/` 下增加一个不依赖 Qt 和子进程的小型辅助模块，负责：

- 为 QSV、NVENC 和 AMF 生成 FFmpeg 硬件解码参数。
- 根据捕获的 FFmpeg 日志判断错误属于硬件设备、字幕或未知错误。
- 根据当前状态决定下一次重试采用的软件解码或无字幕方案。

`EncoderWorker` 继续负责执行 FFmpeg、更新转码进度、清理临时文件以及向界面输出日志。

## 日志行为

- NVIDIA 硬件解码启用时，明确记录当前使用 CUDA 解码。
- 确认硬件设备失败后，记录专门的警告，再降级到 CPU 软件解码。
- 只有确认字幕错误后，才显示丢弃字幕的警告。
- 没有可用降级方案时，保留并显示最终的 FFmpeg 错误日志。

## 测试方案

使用 Python 标准库自带的 `unittest`，不增加新的项目依赖。测试范围包括：

- NVENC 硬件解码参数必须使用 `cuda`，不能包含 `auto` 或 DXVA2。
- 硬件设备错误必须选择 CPU 软件解码降级。
- 字幕错误必须选择删除字幕流。
- 未知错误不能触发重试。
- 整个状态机最多尝试三次，并能正确处理“先字幕错误后硬件错误”和“先硬件错误后字幕错误”两种顺序。

## ab-av1 探测结果修复

### 现有问题

当前程序把 ab-av1 输出中的每个样本行都当作一次完整探测结果。例如同一个 CRF 对 13 个不同视频片段进行评估时，界面会连续显示 13 行相同 CRF、不同 VMAF 的日志。

代码还会在看到任意一条包含 CRF 和 VMAF 的样本行后，将整个探测标记为成功。即使 ab-av1 最终返回 `Code 1` 并报告 `Failed to find a suitable crf`，程序也会强行采用最后一个样本对应的 CRF。该数值既不一定是所有样本的汇总结果，也不一定达到用户设置的目标 VMAF。

ab-av1 默认同时要求：

- 汇总 VMAF 达到 `--min-vmaf`。
- 预测输出体积不超过源视频的 80%。

因此可能出现某个 CRF 达到目标画质但体积超过 80%，下一个 CRF 满足体积要求但 VMAF 略低的情况。此时 ab-av1 会以 `Code 1` 结束，因为没有 CRF 同时满足两个条件。

### 解析规则

新增不依赖 Qt 的 ab-av1 输出解析模块，明确区分：

- `sample N/M crf X VMAF Y`：单个样本结果，只用于内部诊断，不直接显示为最终 CRF。
- `crf X VMAF Y predicted video stream size ... (Z%)`：该 CRF 的汇总结果，记录 CRF、汇总 VMAF 和预测体积百分比，并在界面中每个 CRF 只显示一次。
- `crf X successful`：ab-av1 已正式确认最终 CRF。
- `Failed to find a suitable crf`：没有候选同时满足 VMAF 和默认体积限制。

### 成功与后备选择

- 只有 ab-av1 返回 `0`，且输出包含正式最终结果时，才将探测视为正常成功。
- 如果返回 `Code 1` 的唯一原因是 `Failed to find a suitable crf`，则从完整 CRF 汇总候选中选择：
  1. 汇总 VMAF 达到目标值。
  2. 在满足目标画质的候选中选择最大的 CRF，也就是文件体积通常最小的候选。
- 这种情况下明确记录警告：目标 VMAF 已满足，但预测体积超过 ab-av1 默认限制，并显示候选的汇总 VMAF 与预测体积百分比。
- 如果没有任何候选达到目标 VMAF，则该策略失败并进入下一个探测编码器。
- 如果日志属于编码器崩溃、GPU 设备失败、输入读取失败或其他未知错误，不再强行采用任何临时 CRF，而是进入下一个探测策略。
- 如果所有探测策略都失败，则当前文件标记为失败并询问跳过或停止；不会使用默认 CRF 24 进入正式编码。

### 日志行为

- 每个 CRF 只显示一条汇总日志。
- 不再把单个视频片段的 VMAF 当作整体 VMAF。
- 正常成功、画质优先后备、探测策略失败使用不同日志，避免“异常中止但强行采用”掩盖真实原因。

### 测试

新增标准库单元测试覆盖：

- 多个相同 CRF 的样本行只生成一个 CRF 汇总候选。
- 正常 `successful` 输出返回正式 CRF。
- `Failed to find a suitable crf` 时选择达到目标 VMAF的最大 CRF。
- 达到 VMAF 但超过 80% 体积时允许画质优先后备。
- 所有候选均未达到目标 VMAF时拒绝采用。
- 编码器或设备异常时拒绝采用临时 CRF。
- 所有探测策略失败时拒绝进入正式编码。
