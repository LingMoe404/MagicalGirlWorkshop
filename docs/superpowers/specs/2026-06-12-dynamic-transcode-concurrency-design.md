# v1.4.0 多路动态转码设计

## 背景

当前 `EncoderWorker` 在一个线程中串行处理全部文件。即使显卡拥有足够的编码、解码和显存资源，同一时间也只有一个文件执行 `ab-av1` 探测或 FFmpeg 正式编码。

项目现有的 `thread_limit` 只控制元数据与缩略图读取，不影响转码并发。直接启动多个现有 `EncoderWorker` 会带来以下问题：

- 每个 Worker 都持有整批文件并维护全局进度，职责不适合单文件并发。
- Worker 结束时会扫描并清理整个缓存目录，可能误删其他并发任务的临时文件。
- 错误弹窗直接绑定单一 Worker，多个任务同时失败时无法可靠排队。
- 暂停、停止、系统防休眠和最终完成信号都按单 Worker 设计。
- 相同文件名可能生成相同目标路径，并发时存在覆盖风险。

因此本功能采用“批次调度器 + 单文件 Worker”架构，而不是简单增加线程数。

## 版本规划

本功能作为 `v1.4.0` 发布。

当前工作区中尚未发布的 `v1.3.1` 修复全部并入 `v1.4.0`，包括：

- NVIDIA CUDA 解码优先。
- 硬件解码失败后按错误类型回退 CPU 解码。
- 仅在明确字幕错误时丢弃字幕。
- `ab-av1` 汇总结果解析和画质优先后备。
- 所有探测策略失败时拒绝使用任意默认 CRF。

实施阶段将把版本号从 `1.3.1` 调整为 `1.4.0`，将 `docs/releases/Releases1.3.1.md` 改为 `docs/releases/Releases1.4.0.md`，并把 `CHANGELOG.md` 中尚未发布的 `v1.3.1` 条目合并为 `v1.4.0`。最终发布材料中不保留独立的 `v1.3.1` 发布记录。

## 目标

- Intel QSV、NVIDIA NVENC 和 AMD AMF 均支持多文件并发转码。
- 手动模式支持固定 `1–4` 路并发。
- 自动模式从 `1` 路开始，最多动态提升到 `3` 路。
- 每个文件从 `ab-av1` 探测开始，直到正式编码、输出移动或失败结束，全程占用一个任务槽。
- 并发调整不终止已经运行的文件。
- 错误文件独立等待用户决定，其他任务继续执行。
- 顶部进度显示整批任务的加权总体进度。
- 每个任务拥有独立缓存目录，禁止并发任务互删临时文件。

## 非目标

- 不在同一批任务中同时使用多种编码器。
- 不实现把单个视频切片后由多个编码器并行编码。
- 不依赖 NVIDIA、Intel 或 AMD 专有监控 SDK。
- 不承诺并发越高单文件速度越快；自动模式优化的是整批吞吐量。
- 不恢复被主动终止的 FFmpeg 编码进度。

## 总体架构

### `EncodingCoordinator`

新增批次级调度器，负责：

- 保存待处理、活动、等待错误和已完成任务。
- 根据当前目标并发数启动单文件 Worker。
- 汇总文件进度、速度、状态和日志。
- 执行自动并发升降决策。
- 管理全局暂停、恢复、停止和系统防休眠。
- 串行显示错误决策弹窗。
- 当全部任务结束后只发送一次批次完成信号。

调度器本身不构造 FFmpeg 命令，也不解析 `ab-av1` 或 FFmpeg 日志。

### `EncodeFileWorker`

将现有 `EncoderWorker` 的单文件处理逻辑迁移为单文件 Worker。它负责：

- 获取或补测当前文件元数据。
- 跳过已经是 AV1 的文件。
- 执行 `ab-av1` 探测和探测策略后备。
- 执行 FFmpeg 正式编码与最多三次错误类型降级。
- 上报当前阶段、进度、速度、ETA 和错误原因。
- 移动输出文件并清理自己的临时目录。

Worker 不扫描公共缓存根目录，不直接弹窗，也不控制其他 Worker。

### 纯逻辑模块

新增不依赖 Qt 的调度策略模块，用于：

- 维护并发模式和目标并发数。
- 收集活动 Worker 的速度样本。
- 判断自动模式是否允许升并发或需要降并发。
- 计算批次总体进度。
- 识别硬件资源耗尽类错误。

该模块使用标准库数据类实现，便于单元测试。

## 任务状态

每个文件仅处于以下一种状态：

- `QUEUED`：等待槽位。
- `PROBING`：执行 `ab-av1` 探测。
- `ENCODING`：执行 FFmpeg 正式编码。
- `WAITING_DECISION`：任务失败，等待错误队列处理。
- `SUCCESS`：输出已经安全落盘，或源文件已是 AV1。
- `SKIPPED`：用户或超时决定跳过。
- `FAILED`：批次停止、输出冲突或不可恢复的调度错误。
- `CANCELLED`：用户停止整个批次。

处于 `WAITING_DECISION` 的任务不再占用 GPU 并发槽位。它的子进程和临时输出必须先终止并清理，调度器随后可启动新的排队任务。

## 并发模式

### 手动模式

- 用户设置固定并发数 `1–4`。
- 调度器尽量维持指定数量的活动任务。
- 普通性能下降不会自动改变并发数。
- 如果检测到明确的硬件资源耗尽错误，调度器将本批次目标并发降低一级，并记录警告，避免后续文件持续失败。
- 降级只影响后续补位，不终止当前其他任务。

### 自动模式

- 初始目标并发数为 `1`。
- 自动上限为 `3`。
- 实际活动任务数不超过目标并发数。
- 升降后进入冷却期，避免并发数反复波动。

## 自动并发算法

### 指标

首版使用跨厂商均可获得的指标：

- 所有活动正式编码任务的 `speed=x` 总和。
- 每个活动正式编码任务最近一段时间的速度中位数。
- 活动任务数和阶段。
- CPU 总占用。
- 系统可用内存。
- 硬件设备、显存或编码会话资源错误。

CPU 和内存通过标准库 `ctypes` 调用 Windows `GetSystemTimes` 与 `GlobalMemoryStatusEx` 读取，不增加第三方运行依赖。厂商专有的 GPU 利用率不参与首版核心判定。

`ab-av1` 探测速度不计入吞吐量比较。探测任务仍占用槽位，但自动策略只有在存在稳定的正式编码样本时才做升降判断。

### 稳定窗口

- 正式编码开始后的前 `60` 秒为预热期，不做升并发判断。
- 每个评估窗口为 `90` 秒。
- 每次升降后至少等待 `120` 秒再做下一次调整。
- 活动任务不足以形成完整窗口时保持当前目标。
- 如果评估窗口内有正式编码任务自然结束、失败或被替换，导致活动编码任务集合发生非计划变化，则丢弃该窗口并重新预热，避免把不同视频复杂度造成的速度差误认为并发收益。
- 对于视频很短、始终无法形成稳定窗口的批次，自动模式保守维持当前并发，不为追求升并发而延迟任务。

测试中通过可注入时钟和短窗口模拟，不依赖真实等待。

### 升并发

从 `N` 路尝试提升为 `N+1` 路时：

1. 当前级别已经获得稳定吞吐量基准。
2. CPU 平均占用低于 `85%`。
3. 可用系统内存不少于 `2 GiB`，且不少于总内存的 `10%`。
4. 最近窗口没有硬件资源错误。
5. 当前目标未达到自动上限 `3`。

调度器提升目标后启动一个新任务。新并发级别完成观察窗口后：

- 总吞吐量相对上一级提升至少 `15%`：接受新级别。
- 提升不足 `15%`：将目标降回上一级，并把更高级别标记为本批次不再尝试。

接受新级别后，将该观察窗口的吞吐量保存为新级别基准。后续降级判断只与当前已接受级别的基准比较。

### 降并发

出现以下任一情况时降低目标并发一级，最低为 `1`：

- 连续两个窗口的总吞吐量比当前级别基准低超过 `20%`。
- CPU 平均占用连续两个窗口高于 `92%`。
- 可用内存低于 `1 GiB` 或低于总内存的 `5%`。
- 出现显存不足、编码会话不足、设备忙或硬件资源分配失败。

明确硬件资源错误立即触发降级，不等待两个窗口。

降低目标后：

- 不停止任何正在运行的正常任务。
- 暂停从待处理队列补充新任务。
- 当活动任务自然减少到新目标后恢复补位。

### 无法测量速度

如果编码器长时间不输出可解析的 `speed=x`：

- 自动模式保持当前目标，不盲目升并发。
- 明确资源错误仍允许降级。
- 批次继续运行，不把指标缺失视为文件失败。

## 阶段和槽位

每个活动文件无论处于 `PROBING` 还是 `ENCODING`，都占用一个并发槽。

这样可以避免同时启动大量 `ab-av1` 采样编码，随后又同时进入正式编码而突然超载。调度器不在探测与编码之间释放或重新抢占槽位。

## 缓存隔离

每次批次启动时生成唯一批次 ID，每个文件生成唯一任务 ID：

```text
缓存根目录/
  mgw-session-<批次ID>/
    task-<任务ID>/
      ab-av1/
      output.temp.mkv
```

- `ab-av1 --temp-dir` 指向当前任务的 `ab-av1` 子目录。
- FFmpeg 临时输出固定写入当前任务目录。
- Worker 结束时只能删除自己的任务目录。
- 调度器全部结束后删除空的批次目录。
- 启动清理只删除超过安全时间、且不属于当前活动批次的 `mgw-session-*` 目录。
- 不再通过扫描公共缓存根目录删除所有 `.ab-av1-*` 和 `.temp.mkv`。

## 输出路径冲突

开始任务前统一计算每个输入对应的最终输出路径，并进行规范化比较。

如果两个输入会写入同一个目标：

- 阻止整个批次启动。
- 在界面中列出冲突的输入和目标路径。
- 不自动重命名，也不采用“后完成者覆盖前完成者”。

覆盖源文件模式还需验证输入路径和其他任务输出路径之间不存在交叉覆盖。

## 错误处理队列

### Worker 上报

Worker 发生不可恢复错误时：

1. 终止当前子进程。
2. 清理当前任务临时输出。
3. 上报结构化错误，包括文件路径、阶段、简短原因和日志尾部。
4. 进入 `WAITING_DECISION` 并释放并发槽。

### 调度器处理

- 错误按发生顺序进入 FIFO 队列。
- 主界面一次只显示一个错误弹窗。
- 其他活动任务与队列补位继续运行。
- 用户选择“跳过”后任务进入 `SKIPPED`。
- 30 秒无操作自动选择“跳过”。
- 用户选择“停止”后，调度器停止全部活动 Worker，并把未开始任务标记为 `CANCELLED`。
- 一个文件等待决定时再次收到相同错误事件必须去重。

## 暂停和停止

### 暂停

- 调度器停止启动新任务。
- 所有活动 Worker 进入暂停状态。
- Worker 保持现有“停止读取子进程输出并累计暂停时间”的行为。
- 自动并发评估窗口在暂停期间冻结，暂停时间不计入统计。
- 恢复后所有活动 Worker继续，调度器再按目标并发补位。

### 停止

- 调度器向全部活动 Worker发送停止请求。
- 每个 Worker 终止自己的进程树。
- 关闭或取消当前错误弹窗和待处理错误。
- 未启动任务进入 `CANCELLED`。
- 全部 Worker 退出后再恢复界面状态。

## 系统防休眠

系统防休眠由调度器在批次开始和结束时各调用一次。单文件 Worker 不再单独切换系统休眠状态，避免某个 Worker先结束时错误地解除整批任务的防休眠设置。

## 进度模型

### 文件进度

- `QUEUED`：`0%`
- `PROBING`：映射为 `0–15%`
- `ENCODING`：FFmpeg 进度映射为 `15–100%`
- `SUCCESS`、已是 AV1：`100%`
- `WAITING_DECISION`：保留最后进度。
- `SKIPPED`、`FAILED`、`CANCELLED`：文件行保留最后进度用于诊断，但总体进度计算时按 `100%` 计入，因为这些任务已经没有剩余工作。

如果 `ab-av1` 无法提供连续进度，探测开始显示 `5%`，每完成一个探测策略递增但不超过 `15%`。

### 总体进度

优先按视频时长加权：

```text
总体进度 = Σ(文件时长 × 文件进度) / Σ(文件时长)
```

缺少时长的文件使用当前批次已知文件的中位时长；如果所有时长都未知，则退化为文件进度算术平均值。

当全部文件进入终态后，总体进度强制为 `100%`，无论其中包含成功、跳过、失败还是取消任务。

顶部当前进度条显示总体进度，不再绑定某一个 Worker。界面额外显示：

```text
自动并发 2/3 · 活动 2 · 排队 18 · 等待处理 1
```

每个文件行继续显示自己的阶段、速度、ETA、进度和最终状态。

## 配置与界面

新增设置：

- `transcode_concurrency_mode`：`auto` 或 `manual`，默认 `auto`。
- `transcode_concurrency`：手动并发数，范围 `1–4`，默认 `2`。

设置页增加：

- “转码并发模式”下拉框：自动动态调节、手动固定。
- “手动并发数”数字框：`1–4`，仅手动模式可用。

现有 `thread_limit` 保留并改名为更明确的“元数据读取并发数”，不与转码并发共用。

## 日志

调度器记录：

- 批次启动模式和并发上限。
- 自动模式基准吞吐量。
- 升并发、接受新级别、回退级别的原因。
- CPU、内存或硬件资源保护触发。
- 当前活动、排队和等待错误数量。

Worker 日志增加文件名前缀或任务标识，避免多路日志交错后无法判断来源。

正常样例：

```text
[WTEX-017.mp4] 自动并发提升: 1 → 2，总吞吐量观察开始
[WTEX-018.mp4] 正在推演最强术式 (ab-av1)...
[调度器] 2 路总吞吐量提升 31%，保留当前并发级别
```

## 兼容性

- 并发数为 `1` 时，行为应与现有串行流程等价。
- QSV、NVENC、AMF 共用调度器和动态策略。
- 各编码器原有参数、CRF 偏移、HDR、音频和字幕行为保持不变。
- NVENC CUDA 解码失败后的 CPU 解码回退继续只作用于当前文件。
- 自动模式不要求安装 `nvidia-smi`、Intel 工具或 AMD 工具。

## 测试方案

### 纯逻辑单元测试

- 手动模式固定 `1–4` 路。
- 自动模式从 `1` 路开始且不超过 `3` 路。
- 吞吐量提升达到阈值时接受升级。
- 提升不足时回退并禁止本批次再次尝试该级别。
- 连续吞吐量下降、CPU 高占用、低内存触发降级。
- 硬件资源错误立即降级。
- 降级不取消活动任务，只阻止补位。
- 暂停期间不推进评估窗口。
- 缺失速度样本时不盲目升级。
- 时长加权总体进度及未知时长后备计算。
- 输出路径冲突检测。

### 调度器测试

- 槽位释放后按顺序启动下一个文件。
- `PROBING` 和 `ENCODING` 都占用槽位。
- 错误任务释放槽位，其他任务继续。
- 多个错误按 FIFO 顺序处理且不重复弹窗。
- 自动跳过和“停止全部”决策正确传播。
- 暂停、恢复和停止作用于所有活动 Worker。
- 批次只发出一次完成信号。

### Worker 测试

- 每个 Worker 只处理一个文件。
- 临时目录完全隔离。
- Worker 只清理自己的目录。
- 现有 CUDA/CPU/字幕三次降级测试继续通过。
- 现有 `ab-av1` 正常成功、画质后备和失败保护测试继续通过。

### 冒烟测试

- QSV、NVENC、AMF 至少各执行一次单路兼容性测试。
- 在可用硬件上执行两路真实视频并发，确认输出完整且无互删缓存。
- NVENC 自动模式验证 `1 → 2` 路及吞吐量统计。
- 人为限制资源或注入错误，验证只降低后续目标并发，不终止正常任务。
